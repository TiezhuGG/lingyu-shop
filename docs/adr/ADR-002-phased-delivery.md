# ADR-002：分阶段交付、后端复用与任务基础

日期：2026-10-08。状态：采纳为实施设计，代码尚未落地。

## 背景

用户明确先完成 5000 原型，再完成 50000 原型。现有八包工程只有占位入口，原任务工作包过大；API/Worker 如何共享业务没有实际代码边界；超时订单所需任务基础排在订单/支付之后。总体设计末尾的 ADR 列表是建议主题，不是实际文件编号；已有 ADR-001 工程基线保留，本文件为实际 ADR-002。

## 决策

1. 保留现有运行时、四应用、模块化单体和 PostgreSQL/Prisma。两端 Vue/Vite 保持各自已验证版本，不强制去重或升级。
2. 默认 P1-A 中间体验交付→P1-B 真实交易完整验收→P2 增量实现。演示通过不等于真实功能完成；改变阶段门槛需在任务/进度记录用户选择。
3. T01-D 实际新增 packages/server-modules，供 API/Worker 共用应用服务、领域与仓储适配。backend-shared 只放小型 Money/Quantity/事务端口；contracts 只含客户端契约。新增包同批更新 workspace 检查、依赖、exports 与构建验证。
4. 首版任务基础采用 PostgreSQL Outbox/Inbox/job_run + 租约 + 有限重试；Redis 按需用于缓存/限流。BullMQ 仍为扩展候选，采用前验证兼容性并新增 ADR。
5. T12-A 在 T09 之前交付；订单超时、支付查单、退款查单等消费者随 T09/T10 交付，T12-B 汇总恢复与人工重放验证。
6. P2 的多仓、批次效期、称重、AI、平台分账作为可选扩展，原型全部入口的完成不依赖这些未明确要求的能力。

## 备选与取舍

- API 与 Worker 各自实现规则：容易出现库存/退款行为分歧，放弃。
- Worker 直接导入 apps/api 内部目录：形成入口间耦合与编译部署问题，放弃。
- 全部后端写入 backend-shared：破坏小型内核边界，放弃。
- 首批同时部署 Redis 队列/缓存和完整营销平台：增加尚未验证的依赖，推迟。

数据库任务轮询增加数据库负载，因此控制领取批量、轮询退避和索引；生产连接总预算包含 Worker。若实际队列吞吐/调度精度不达标，按测量结果换任务适配器，保留 Outbox 与业务幂等键。

## 验证与回退

T01-D 验证两个入口能装配同一服务而无前端后端依赖污染，构建顺序可复现；T12-A 验证崩溃租约恢复、重复领取、提交前后故障、消费幂等。规则实现升级 API/Worker 同版本发布；切队列实现不删除未消费事件，先并存验证、按消费者键去重再切换。
